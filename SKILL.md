# Procedural Isometric Worlds

Create an original, readable miniature world whose assets are generated by code. The reusable idea from WareTrack is a family of small asset factories, an orthographic camera, a coordinated palette, soft shadows, and simulation state driving transforms. A new theme needs new silhouettes and interactions, not merely replacement labels.

## Choose the scope

Follow the user's theme, framework, and requested complexity. Inspect an existing app before changing its renderer or dependencies. An asset request needs a reusable factory and preview; a scene needs composition and controls; a simulation needs a visible working loop and state. Do not expand a visual request into WareTrack's entire economy or progression system.

For a fresh static prototype, copy [assets/starter/](assets/starter/) into the destination. It contains an original garden center with moving carts, editable planting beds, canvas signage, instanced trees, selection, and orthographic pan/zoom/rotation. Serve over HTTP with `python3 -m http.server 8000 --bind 127.0.0.1` from the copied directory. It uses Three.js **0.180.0** ES modules via an import map; network access is required for the pinned CDN modules. Adapt its domain factories and layout rather than shipping the garden unchanged.

For an existing React/Vite/etc. app, use its installed Three.js version and lifecycle. Extract the factory concepts instead of imposing a new project structure. Keep core and addon imports on the same version. WareTrack uses r128 globals; do not mix its API conventions into a modern module app.

## Build the visual grammar

- Choose one unit scale, Y-up, an XZ ground plane, and consistent asset origins at ground center. Record each factory's forward direction; the starter cart faces +X.
- Use a compact palette: pale ground, cool shadows, structural neutrals, and a few saturated colors for functional objects. Flat color plus lighting carries the style; texture noise usually weakens it.
- Start with ground, paths, and a few recognizable assets. Judge silhouettes at the intended camera zoom before adding fine details. A building reads from body + roof + entry; a vehicle reads from body + cab + wheels; machinery needs one distinctive working part.
- Use orthographic projection with approximately 45° azimuth and 35.264° elevation as an initial isometric view. Refit the frustum to the canvas aspect ratio and account for panels/mobile controls. Use positive near/far clipping values appropriate to the scene.
- Begin with hemisphere fill and one directional sun, rough nonmetallic materials, shadow-receiving ground, and shadows on major shapes. Tune intensity for the actual Three.js version; modern color and lighting defaults differ from r128.

## Assemble assets

Prefer `THREE.Group` factories built from boxes, cylinders, low-segment spheres, cones, and small custom extrusions. Geometry primitives are centered: a ground-resting box of height `h` needs center Y = `h/2`. Rotate wheel cylinders 90° so their axes match the axle.

Return the group plus named references to moving subparts; attach an entity identifier for picking. Use configuration for dimensions, colors, signs, and meaningful variants. Cache geometry and static materials by all relevant parameters. Shared materials make global recoloring easy; an independently blinking beacon or transparent shell needs its own material.

Use Canvas 2D → `THREE.CanvasTexture` → plane or sprite for lettering, decals, roof logos, road arrows, and badges. Mark color textures as `THREE.SRGBColorSpace` in modern Three.js. Wait for custom fonts before drawing labels. Keep decals slightly off surfaces to avoid z-fighting; choose plane orientation deliberately. Update `texture.needsUpdate` only when redrawing.

Read [references/construction-patterns.md](references/construction-patterns.md) for domain recipes, batching, and lifecycle choices. Read [references/waretrack-rendering.md](references/waretrack-rendering.md) when explaining or adapting the reference's exact implementation.

## Animate articulated assets

For a robot, mechanical character, or reusable animated machine, read [references/articulated-animation.md](references/articulated-animation.md). The working [assets/robot/](assets/robot/) example has a configurable robot factory, shoulder/elbow/hip/knee/head pivots, idle/wave/walk/dance motions, procedural face blinking, and GLB export with four baked joint-animation clips. Copy the whole example for a standalone preview, or reuse `robot.js` in an existing Three.js scene.

Place pivots at actual joints and build moving parts beneath them. Keep asset generation, pose updates, and scene/UI setup separate. Blend joint transforms into new modes using seconds-based damping, expose pause/resume, and honor reduced motion in the preview. Parameterize proportions and colors without rebuilding the rig every frame. If the user wants an animated downloadable model, export transform animation clips explicitly; a posed GLB by itself does not preserve procedural motion. State which effects remain runtime-only (the example's canvas eye blinking is not baked into GLB).

## Make the world interactive

Keep simulation records separate from scene nodes. Factories create nodes; updates change transforms from state. Use a clamped seconds-based delta, wrapped angle interpolation, and bounded waypoint movement. Do not rebuild meshes every frame. Let moving parts explain the process: lift carriage, conveyor load, crop growth, gate arm, or crane boom.

Raycast within the canvas bounding rectangle, recurse through groups, and climb parents to the entity identifier. For instances, resolve `instanceId` through a parallel entity array. Distinguish a click from a camera drag. Show selection with an outline/ground marker and meaningful HTML details. Project world coordinates to screen only for labels that need to follow an entity.

Prefer semantic HTML controls and inspectors over drawing the whole interface into WebGL. Provide a DOM entity list when objects need keyboard access. Keep UI events from triggering scene actions. For interiors, group obstructing walls/roofs separately and fade or hide them when the camera needs to reveal work; manage transparent depth writing carefully.

## Keep rendering scalable

Geometry/material caches reduce allocation, **not draw calls**. Instance repeated static meshes such as trees, lamps, roads, crop patches, and structural parts when scene size warrants it. Update instance matrices/colors and bounds after changes. Keep dynamic entities in groups unless batching them helps at the measured scale.

Limit pixel ratio, shadow resolution, and the shadow frustum to what the view needs. For large worlds, partition instances by region and simplify distant inactive sites. Removing a node does not dispose GPU resources: dispose owned unique geometries, materials, textures, and instance buffers on teardown; retain shared resources until their owners release them. In framework apps, also stop animation loops, disconnect resize observers, and remove listeners on unmount.

## Verify and deliver

Open the scene in the available browser. Check load/console errors, recognizable silhouettes, text orientation, shadow contact, desktop/mobile framing, pan/zoom, selection, and one meaningful state transition. For moving processes, verify pause and resume. Inspect `renderer.info` when scaling/rebuilding to find draw-call or resource growth. Report behavior that remains unverified if browser access is unavailable.

Deliver working files and the launch command, summarize the new theme's factories/interactions, and name actual external runtime dependencies. Example request: “Use $procedural-isometric-worlds to build an interactive recycling depot with conveyors, sorting bins, trucks, and a live material-flow inspector.”
